This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

**Keep this file current: after any change that touches architecture, data flow, commands, or conventions described below, update the relevant section in the same turn rather than letting it drift.**

## Project

A "Life in the UK" citizenship test practice app: 1,196-question bank (topic-tagged, browsable/searchable), randomized 24-question sessions (official test length, 75% pass mark), SM-2 spaced repetition to resurface weak questions, and progress stats. Built with Next.js 16 (App Router), React 19, Tailwind v4. Question bank, progress, and history are backed by Neon Postgres; sign-in is Neon Auth (Google or email/password, via `@neondatabase/auth`) — see "Neon migration" below for the one open item.

## Git

Never run `git commit` (or push) in this repo unless the user explicitly asks in that exact turn. Leave changes staged/unstaged for the user to commit themselves.

## Commands

- `npm run dev` — start dev server (Next.js dev, Turbopack/webpack)
- `npm run build` — production build (`next build`); use this to check for TS/build errors, there is no separate typecheck/lint script
- `npm run start` — serve the production build
- `npm run analyze` — production build with `@next/bundle-analyzer` enabled (`ANALYZE=true next build`), opens per-route bundle treemaps; use to check for unused/oversized client JS
- `npm run migrate` — apply any pending files in `db/migrations/` in order (tracked via the `schema_migrations` table, safe to run repeatedly — see "Database migrations" below); leaves `questions` empty (schema only), see `sync:questions` below to populate it
- `npm run export:questions` / `npm run sync:questions` — dump/restore the live `questions` table to/from a gitignored review file; `sync:questions` is also the sole bootstrap path for a freshly-migrated empty `questions` table, see "Question review/sync workflow" below

There is no lint script configured in `package.json` — don't invent `npm run lint`. E2e tests live in `e2e/` (Playwright, `@playwright/test`) — run via `npm run test:e2e`. **Use Playwright to verify UI/behavior changes** rather than claiming it's untestable: `npx playwright test` runs headless Chromium fine in this dev environment (confirmed working, `npx playwright install chromium` succeeds). Write/extend specs under `e2e/public/` (signed-out flows) or `e2e/signed-in/` (mock-auth flows, via `e2e/fixtures/auth.ts`'s `signedInPage` fixture) when validating a change, in addition to `npm run build` plus manual `curl`/direct-SQL checks. Note the mock-auth fixture only fakes the client-side session check (`authClient.useSession()`, via intercepting `GET /api/auth/get-session`) — it does not make server-side `auth.getSession()` calls in API routes (`/api/progress`, `/api/history`, `/api/account`) see a signed-in user, since those hit the hosted Neon Auth backend directly; e2e specs can assert signed-in UI shell/rendering but not real signed-in persistence without a deliberate test-only bypass (not implemented — flag it if a task needs one, don't add it silently). There's no separate Neon test branch — e2e tests run against the same `DATABASE_URL` as `npm run dev`; anonymous quiz progress is in-memory only (see SM-2 section below) so this doesn't pollute persisted data.

`NEXT_PUBLIC_SESSION_SIZE` (in `.env.local`) overrides the default 24-question session length for faster manual testing during dev. All env vars are read through `src/config.ts` — add new ones there rather than calling `process.env.X` directly in other files.

## Architecture

### Neon migration (complete, one open item)

The app was migrated off `localStorage`/static-array/Vercel-KV storage onto Neon Postgres, tracked in `docs/superpowers/plans/2026-07-22-neon-migration.md` (gitignored — local-only reference, not committed). Current state:
- `questions`/`progress`/`history` tables (`db/migrations/0000_baseline.sql`); `src/db.ts` exports the shared `sql` client (`@neondatabase/serverless`). Question content (currently ~1,196 rows) has no in-repo static source — it lives only in the live Neon `questions` table plus the gitignored `db/questions-export.json` (tracked separately, outside this repo, in a private `.git-private` store — see "Question review/sync workflow" below); `npm run sync:questions` is the only way to populate a fresh/empty `questions` table.
- `/api/questions`, `src/quiz/loadQuestions.ts`, `src/ReviewPage.tsx`, `app/questions/page.tsx` all read questions from Postgres (no client-side cache — every call hits the API). `/api/progress`, `/api/history` read/write the Postgres `progress`/`history` tables (see "SM-2" below) — signed-in users' progress/history is fetched from these routes into in-memory app state on sign-in; there is no client-side persistence layer for this data (see "App-state layer" below).
- `next-auth` and `@vercel/kv` are fully removed (`auth.ts` deleted, both packages uninstalled). Sign-in runs on `@neondatabase/auth` (Neon Auth): `lib/auth/server.ts` (`createNeonAuth()`, reads `NEON_AUTH_BASE_URL`/`NEON_AUTH_COOKIE_SECRET` from `src/config.ts`), `lib/auth/client.ts` (`createAuthClient()`), `app/api/auth/[...path]/route.ts` (`auth.handler()`). Both Google OAuth and email/password sign-up/sign-in are enabled entirely in the Neon Console dashboard — `NeonAuthConfig`/`createAuthClient()` take no `providers`/`emailAndPassword`/`plugins` options in this repo's code, so there's nothing to toggle here beyond the UI. `src/SignInPage.tsx` (`/sign-in?callbackURL=...&mode=signin|signup`) is the single place `authClient.signIn.social()`/`signIn.email()`/`signUp.email()` are called; `src/Header.tsx`, `src/SignInNudge.tsx`, and `src/quiz/SignInPromptModal.tsx` all link out to it rather than calling `authClient` directly. Neon Console's email/password toggle **does** require OTP email verification before a session is granted (confirmed — better-auth's `emailOTP` plugin, mailed as a 6-digit code, 10min expiry): when `signUp.email()` succeeds without returning a session token, `SignInPage.tsx` shows a code-entry form (`authClient.emailOtp.verifyEmail({email, otp})`, with a `sendVerificationOtp()`-backed "Resend code" button) rather than assuming failure. The OTP-verification state (`awaitingVerification`, the entered code, etc.) is plain `useState`, not persisted — a reload or a new tab loses it, and an unverified account can neither sign in (`email_not_confirmed` error) nor re-signup (`user_already_exists` error) through the normal paths, a real dead end otherwise. `submit()`'s sign-in branch specifically catches `code === "email_not_confirmed"`, fires a fresh `sendVerificationOtp()`, and re-shows the OTP screen instead of the generic "Invalid email or password." — this is the sole recovery path back into a stuck unverified signup, so don't remove it thinking it's dead code. Password reset is also OTP-based (confirmed by probing both endpoints directly: `POST /api/auth/forget-password`, the link-based better-auth endpoint, 404s — Neon Console has only the `emailOTP` plugin's `/email-otp/request-password-reset` and `/email-otp/reset-password` enabled, both 200). `SignInPage.tsx`'s "Forgot password?" link (signin mode only) drives a two-step `forgotStep: "request" | "reset"` flow: `authClient.emailOtp.requestPasswordReset({email})` sends the code (always resolves 200 regardless of whether the email exists, so this path doesn't leak account existence — don't add a client-side "no account with that email" branch, there's nothing to branch on), then `authClient.emailOtp.resetPassword({email, otp, password})` completes it. `resetPassword` doesn't return a session token (unlike `signUp.email`/`emailOtp.verifyEmail`), so on success the UI drops back to sign-in mode with a `resetSuccessMessage` rather than auto-redirecting — the user still has to sign in with the new password. **Important footgun**: `@neondatabase/auth`'s client fetch layer always throws (`AuthApiError`) on any non-2xx response regardless of the `throw` fetch option — every `authClient.*` call in this file (`signIn.email`, `signUp.email`, `emailOtp.verifyEmail`, `emailOtp.sendVerificationOtp`, `emailOtp.requestPasswordReset`, `emailOtp.resetPassword`) is wrapped in try/catch, not a `{data, error}` destructure/check, unlike what plain better-auth docs suggest.
- Next.js was upgraded 15→16.2.11 as part of this migration (`@neondatabase/auth` hard-requires `next >=16.0.0`).
- `tsconfig.json` excludes `scripts/` from typecheck so files like `scripts/migrate.ts`/`scripts/sync-questions.ts` can use `.ts` extensions in their relative imports (required for standalone `node --experimental-strip-types` execution) without breaking `next build`.
- **Open, accepted risk:** `@neondatabase/auth` pins `better-auth@1.4.18`, which has a **critical** unpatched CVE bundle (OAuth state-mismatch bypass, account takeover via unverified-email auto-link, stored XSS via `redirect_uri`, refresh-token replay). No 1.4.x patch exists (next release is 1.5.1). Decision made: proceed accepting this as a beta-software limitation, revisit when Neon ships a patched release — don't re-raise this as a blocker unless asked to reassess.

### Database migrations (`db/migrations/`)

Schema changes are numbered, ordered `.sql` files in `db/migrations/` (e.g. `0001_add_foo.sql` — always 4-digit zero-padded, since ordering is plain lexicographic filename sort, not numeric: an unpadded `10_x.sql` would sort before `0002_x.sql`), applied by `scripts/migrate.ts` (`npm run migrate`) — a `schema_migrations` table (`id`, `applied_at`) tracks which files have already run, so the command is always safe to re-run: pending files get applied in filename order, already-applied ones are skipped. `0000_baseline.sql` is the historical starting point — every table that existed before this system was introduced, moved verbatim from the old `db/schema.sql` (which no longer exists). All migrations must be idempotent (`CREATE TABLE IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`, etc.) since a failed migration's already-run statements aren't rolled back (the Neon serverless driver doesn't support wrapping arbitrary raw SQL text in a transaction) — a retry re-runs the whole file from its first statement. The runner splits each file into statements on a plain `;` (the Neon driver rejects true multi-statement calls) — this only supports simple semicolon-terminated DDL; a migration containing a `DO $$ ... $$` block, a function/trigger definition, or a semicolon inside a string literal will be silently mis-split and fail (or worse, run a truncated statement) — keep migrations to plain single-statement-per-`;` DDL. To add a schema change: create the next-numbered `.sql` file, then run `npm run migrate`.

### Question review/sync workflow (`scripts/export-questions.ts` + `scripts/sync-questions.ts`)

`npm run export:questions` dumps every row of the live `questions` table (`id, question, options, answer, explanation, topic`, ordered by `id`) to `db/questions-export.json` — gitignored, local-only, for hand-reviewing/editing question text, options, or answers outside the app; also tracked separately outside this repo (in a private `.git-private` store) so it survives a fresh clone. `npm run sync:questions` reads that file back and upserts every row into `questions` by `id` (`INSERT ... ON CONFLICT (id) DO UPDATE`) — this is the **only** way question content gets into the table (there is no static in-repo seed source), so it's also the bootstrap path for a freshly-migrated, empty `questions` table: run `npm run migrate` then `npm run sync:questions` against a copy of `db/questions-export.json`. Both scripts read `DATABASE_URL` straight from the environment like every other `scripts/` file — the npm scripts default to dev via `.env.local`; to target prod, run with prod's `DATABASE_URL` in scope instead (e.g. `DATABASE_URL="<prod-url>" node --experimental-strip-types scripts/sync-questions.ts`), once for each environment.

**Deletion is out of scope by design.** `questions.id` is referenced by `progress.question_id` and `feedback.question_id` (`db/migrations/0000_baseline.sql`, no `ON DELETE` action), so removing a row from the review file is never treated as "delete it" — a row missing from the file is simply left untouched in the table. This is the mechanism that keeps those two foreign keys intact across a review/sync round-trip: `id` is never reassigned or dropped, only inserted (new) or updated in place (existing).

### Route/component split

`app/*/page.tsx` files are thin wrappers that just render a same-named component from `src/` (e.g. `app/test/page.tsx` renders `src/QuizPage.tsx`). The actual page logic lives in `src/`, `app/` only defines routes:
- `/` → `src/HomePage.tsx`
- `/sign-in` → `src/SignInPage.tsx` (Google + email/password sign-in/sign-up, tab-toggled via `?mode=signin|signup`, redirects to `?callbackURL=...` on success or if already signed in)
- `/test` → `src/QuizPage.tsx`
- `/review` → `src/ReviewPage.tsx`
- `/profile` → `src/ProfilePage.tsx` (identity block, sign out, a nav hub to `/stats`/`/friends`/`/propose-question` via `src/NavCard.tsx`, self-service account deletion — signed-out visitors see a `src/SignInNudge.tsx` CTA in place of everything else, no redirect). Deliberately **not** a stats page — see "Stats vs Profile vs Friends" below.
- `/questions` → question bank browser (topic-chip filtering + live fuzzy search via `src/SearchBox.tsx`, paginated)
- `app/layout.tsx` renders `src/AuthSync.tsx` (no-UI component that syncs Neon Auth session state into `src/authState.ts` and, via `useProgress()`/`useHistoryState()`, calls their `refreshFromServer()` on sign-in) and `src/Header.tsx` (shared header: logo, sign-out via `authClient` from `lib/auth/client.ts` / sign-in link to `/sign-in`, avatar link to `/profile`, contextual back-link/stats-row per route via `usePathname()`). Neon Auth's client hooks (`authClient.useSession()`) don't require a context provider, but `AuthSync` is rendered *inside* the app-state provider tree (see below) since it consumes those contexts.

Modals that render conditionally (`AppFeedbackModal` in `src/HomePage.tsx`, `SignInPromptModal` in `src/QuizPage.tsx`, `ReportModal` in `src/quiz/FeedbackPanel.tsx`) are imported via `next/dynamic({ ssr: false })` rather than a static import, so their JS is a separate chunk that only loads when actually opened, not inlined into the parent route's initial bundle. Follow this pattern for any new modal/rarely-shown component.

### The quiz engine (`src/quiz/`)

Fully idiomatic React (rewritten from a legacy imperative DOM-manipulation engine — `reactStrictMode` is enabled, no special coupling to worry about). `src/quiz/useQuizEngine.ts` is a custom hook wrapping a `useReducer` (`src/quiz/reducer.ts`, pure — no I/O) that models session state as `{ phase: "loading"|"active"|"results", sessionQueue, currentQuestion, selectedOptions, currentDisplayOptions, answered, lastResult, ... }`.

`src/quiz/QuizContext.tsx`'s `QuizProvider` (just `useQuizEngine()` + context, no side behavior) is mounted **once, at `app/layout.tsx`** (inside `HeaderStatsProvider`, wrapping `<AuthSync/><Header>{children}</Header>`) rather than inside `QuizPage.tsx` — this is deliberate: it means the reducer state survives client-side navigation away from `/test` and back (the provider never unmounts on route change), so an in-progress test resumes where it was left. `useQuizEngine()` no longer auto-starts a session on mount; it exposes `start()`, guarded by a `startedRef` so it's a no-op after the first call (idempotent against remounts and Strict Mode's double-invoke). `src/QuizPage.tsx`'s mount effect calls `start()` only `if (state.phase === "loading")` — i.e. only the very first time the engine is used — and separately owns the keyboard-shortcut listener (digits 1-9 select options, Enter/Space advances) via its own `useEffect`, scoped to `/test` only (it would misfire on other routes if it lived in the layout-level provider). `useQuiz()` reads the engine from context so presentational components (`QuestionCard`, `OptionsList`, `OptionButton`, `FeedbackPanel`, `ReportModal`, `ResultsScreen`, `NavigationBar`, all in `src/quiz/`) never prop-drill.

A full page reload also resumes the in-progress session rather than starting a fresh randomized one: `useQuizEngine.ts` mirrors the reducer `state` to `sessionStorage` (key `quizActiveSession`) via a `useEffect` that skips writes while `phase === "loading"` (so the pre-`start()` placeholder state never overwrites a real stored session, regardless of effect-ordering between the layout-level provider and `QuizPage`'s mount effect). **The persisted copy strips each question's `a` (correct answer index/indices) and `ex` (explanation)** via `stripAnswer()` before it's written — both are otherwise plaintext-readable in devtools while a question is still unanswered, which would let a user look up the correct answer before picking one; every other field (question text, options, sm2/accuracy snapshot) is harmless to store since it doesn't reveal correctness. `start()` checks that key first — if present, it re-fetches the live question bank (`loadQuestions()`, the same call a fresh session start already makes) and merges each stored question's real `a`/`ex` back in by id before dispatching `SESSION_RESTORED` (reducer case: `return action.snapshot`), so in-memory state is immediately whole again — `OptionsList` still needs `question.a` at render time (multi-select detection, and revealing the correct answer once answered) regardless of restore path, it's just never sourced from the stored snapshot. If a stored question's id no longer resolves in the bank (edge case — bank changed since the session started) and `phase` was `"active"`, restore is abandoned in favor of a fresh `buildSessionQueue()` call rather than dispatching a broken snapshot. `sessionStorage` (not `localStorage`) is deliberate — it survives a reload but not a closed tab, matching the app's existing tab-scoped-only semantics for anonymous session data (see below) and never resurrects a stale session into a new tab. `restart()` (used by "Start New Test") is unaffected — it still dispatches a fresh `SESSION_STARTED`, which the same persistence effect then overwrites the stored snapshot with on the next render.

**Side effects (SM2 saves via `useProgress().recordAnswer()`, history saves via `useHistoryState().recordResult()`) are sequenced in the hook's action-creator functions (e.g. `submitAnswer()`, `next()`), never inside the reducer** — the reducer must stay pure since it's exercised by dispatch, while action creators run once per event regardless of Strict Mode. `src/quiz/loadQuestions.ts` fetches `/api/questions` directly on every call, no caching.

`src/Header.tsx` renders the quiz session's live total-questions/score, but it's a tree-**ancestor** of `QuizPage` (`app/layout.tsx` wraps `<HeaderStatsProvider><QuizProvider><Header>{children}</Header></QuizProvider></HeaderStatsProvider>`), so that data can't flow up through normal props. `src/headerStats.tsx`'s `HeaderStatsProvider`/`useHeaderStats()` context (provided above both `QuizProvider` and `Header` in `layout.tsx`) solves this cleanly: `useQuizEngine.ts` calls `setTotalQuestions()`/`setScore(current, total, animate)` on the context, and `Header.tsx` reads those values and renders them declaratively — no DOM reaching between components. The one remaining imperative bit is contained entirely inside `Header.tsx` itself: a `useEffect` on its own `scoreRef` calls `animateNumber()` to tween the score display when `animate` is true (matching the original's "only animate on first-try-correct" behavior), otherwise sets `textContent` immediately — the same pattern `src/quiz/ResultsScreen.tsx` uses for its own counter. The header's accuracy stat is fully declarative — `Header.tsx` computes it directly from `useProgress().aggregate` in JSX, no DOM writes or animation (unlike the score counter, which is a deliberately-kept imperative exception). Confetti (`src/quiz/confetti.ts`) and `src/animateNumber.ts` remain small imperative helpers invoked from `useEffect`s/handlers, by design — not reimplemented in pure React.

### SM-2 spaced repetition (`src/sm2.ts` + `src/progressContext.tsx`)

Each question tracks `{ n, ef, i, next, attempts, correct, lastCorrect?, lastSelected? }`. **This data lives only in React state** (`src/progressContext.tsx`'s `ProgressProvider`, a `Record<number, SM2Data>`) — there is no `localStorage` involved. For anonymous users this means progress is lost on refresh (a deliberate tradeoff — see "App-state layer" below); for signed-in users, `AuthSync.tsx` calls `useProgress().refreshFromServer()` on sign-in, which fetches `/api/progress` and merges it into state. `buildSessionQueue()` in `src/quiz/useQuizEngine.ts` builds each session from three buckets — new (`attempts === 0`), needs-improvement (`correct < attempts`), mastered (`correct === attempts`) — at a fixed 80/15/5 ratio (`SESSION_NEW_RATIO`/`SESSION_IMPROVE_RATIO`/`SESSION_CORRECT_RATIO` in `src/config.ts`), sorting each bucket by `next` (overdue first) then historical accuracy (weakest first), with a shortfall fill (new → improve → correct) when a bucket is too small. This mix is deliberate: sorting the *whole* bank by `next` alone (the pre-2026-07-23 behavior) put unseen questions first unconditionally, since `next: 0` for unseen questions is always less than any real due-timestamp — meaning previously-wrong questions never resurfaced until the entire 1,196-question bank had been seen once.

`src/history.ts` + `src/historyContext.tsx` work the same way for completed-session scores (capped at 50 entries in state, no persistence) — this feeds `ProfilePage`'s time-series chart, distinct from the per-question SM-2 store.

Signed-in users' data is durable via Postgres regardless of what's in browser state: `/api/progress`/`/api/history` read/write the Postgres `progress`/`history` tables (`src/db.ts` + `lib/auth/server.ts`'s `auth.getSession()`). `progress.next`/`history.completed_at` are `BIGINT` columns and come back from `@neondatabase/serverless` as strings — always `Number(...)`-convert them; `history.completed_at` stores the client's own `Date.now()` value verbatim (not a DB-generated timestamp), since `useHistoryState().refreshFromServer()` dedupes by exact `timestamp` equality. Anonymous users' progress is genuinely ephemeral (tab/session-scoped only) — this is intentional, not a bug.

### App-state layer (`src/*Context.tsx`)

Five sibling Context/hook pairs, mounted in `app/layout.tsx` wrapping `<Header>` (same reasoning as `HeaderStatsProvider`: `Header`/`ThemeToggle`/`CookieBanner`/`AuthSync` all need this data and aren't inside `QuizPage`'s tree):

- `src/progressContext.tsx` → `useProgress()`: `{ aggregate, getSM2(id), recordAnswer(id, sm2Data), refreshFromServer(), reset() }` — pure in-memory `Record<number, SM2Data>`, no persistence, no DOM writes (`aggregate` is read declaratively wherever it's needed, e.g. `Header.tsx`'s accuracy stat). `getSM2()` always returns a fresh copy (never the shared default object or a live reference into state) since `useQuizEngine.ts`'s `submitAnswer()` mutates the returned object before re-saving it.
- `src/historyContext.tsx` → `useHistoryState()`: `{ history, recordResult(score,total), refreshFromServer(), reset() }` — pure in-memory `TestResult[]`, no persistence.
- `src/feedbackContext.tsx` → `useFeedbackState()`: `{ hasReported(id), markReported(id), reset() }`, wraps `feedback.ts` (still `localStorage`-backed under `ukTestReportedQuestions` — out of scope for the progress/history/session removal, unchanged).
- `src/themeContext.tsx` → `useTheme()`: `{ isDark, toggleTheme() }`, still `localStorage`-backed (`"theme"`).
- `src/cookieConsentContext.tsx` → `useCookieConsent()`: `{ hasConsented, accept() }`, still `localStorage`-backed (`ukTestCookieConsent`).

`recordAnswer`/`recordResult`/`markReported`/`toggleTheme`/`accept` update their context's React state synchronously (and, for progress/history, POST to `/api/progress`/`/api/history` when signed in) — no `useEffect`-deferred writes, since `useQuizEngine.ts`'s Strict-Mode-safe "write before dispatch" discipline (see above) depends on that timing being preserved exactly. `app/layout.tsx`'s pre-hydration `THEME_INIT_SCRIPT` (prevents flash-of-wrong-theme) is untouched and still the sole authority on the initial DOM class; `ThemeProvider` only mirrors that DOM state into React after mount, it doesn't drive it.

**No `*Context.tsx` component reads/writes `localStorage`/`sessionStorage` directly** — only `src/feedback.ts`, `src/themeContext.tsx`, and `src/cookieConsentContext.tsx` still touch `localStorage` (all three deliberately out of scope when progress/history/session persistence was removed). The one exception to "no `sessionStorage`" is `src/quiz/useQuizEngine.ts`, which mirrors the active quiz session to `sessionStorage` so a page reload resumes it instead of randomizing a new one (see "The quiz engine" above) — this is intentionally tab-scoped-only, same as the in-memory SM-2/history state it sits alongside, just surviving one additional case (reload) that plain React state can't.

### Styling

Tailwind v4, wired through `@tailwindcss/postcss` (not the Vite plugin, since Next.js doesn't build with Vite). Design tokens are defined once via `@theme` in `src/style.css` (`--color-accent`, `--color-good`/`--color-bad` + `-soft` variants, etc.) — use these token classes (`bg-accent`, `text-good`, ...) rather than raw Tailwind palette colors, to stay consistent with the rest of the UI.

**MUI X Charts** (`@mui/x-charts`, plus its required peers `@mui/material`/`@emotion/react`/`@emotion/styled`) is the app's one non-Tailwind UI dependency: `LineChart` in `src/ScoreChart.tsx` (score-over-time, `StatsPage`'s sole caller — see "Stats vs Profile vs Friends" below for its current pass/fail-gradient design), `BarChart`s in `src/StatsPage.tsx` ("You vs average", "You vs your friends") and `src/TopicAccuracyChart.tsx` (per-topic accuracy, weakest-first), and `Gauge` via `src/StatGauge.tsx` (reusable radial gauge tile — red/accent/green by value, used for every percentage-scale stat on `HomePage`/`ProfilePage`/`StatsPage`; count-scale stats like "Tests taken" stay plain number tiles since they don't fit a 0-100 gauge). `src/muiTheme.ts`'s `getMuiTheme(isDark)` bridges the two systems — it builds an MUI theme from hex literals mirrored from `style.css`'s light/dark tokens (not a runtime `getComputedStyle` read, to avoid an SSR/client mismatch) — and `CHART_TOKENS` exports the same values directly for per-series bar/line/gauge colors. Every chart-bearing component reads `isDark` from `src/themeContext.tsx`'s `useTheme()` and wraps its chart in `<ThemeProvider theme={getMuiTheme(isDark)}>` locally (no app-wide MUI provider in `app/layout.tsx` — Next's route-level code splitting already keeps this weight out of every other route). The "You vs your friends" bar chart drops per-row avatars (not feasible as native MUI bar labels) in favor of a small ranked avatar strip rendered above the chart. Horizontal `BarChart`s always set `yAxis[0].width: "auto"` (not a fixed `margin.left` guess) — the app's content column is a narrow `max-w-xl`, so a fixed margin reliably ellipsis-truncates longer category labels (topic names, friend names); `"auto"` measures the real label text and sizes the axis to fit. `src/topics.ts`'s `topicShortLabel()` (distinct from the full `topicLabel()` used elsewhere, e.g. the question-card topic chip) exists specifically for this chart's y-axis, where even `"auto"`-sized full topic names would eat most of the chart's width in that narrow column.

`TopicAccuracyChart` needs per-question topic data that no existing context exposed: `useProgress()` gained a `getAllProgress()` selector (returns the full `Record<number, SM2Data>`, not just the summed `aggregate`) alongside a new lightweight `GET /api/questions/topics` endpoint (`{id, topic}[]` only — deliberately not the full `/api/questions` payload, which includes options/answers/explanations this chart doesn't need) to map progress IDs to topics client-side.

### Auth

See "Neon migration" above for the full picture — in short: `lib/auth/server.ts` (`createNeonAuth()`) for server components/API routes via `auth.getSession()`, `lib/auth/client.ts` (`authClient`) for client components via `authClient.useSession()`/`authClient.signIn.social(...)`/`authClient.signOut()`, `app/api/auth/[...path]/route.ts` proxies everything to Neon's auth server. No `middleware.ts` exists and none is needed — every route works fully signed-out.

`src/SignInNudge.tsx` is a small shared presentational CTA card (title/body/callbackURL props, calls `authClient.signIn.social`) used to nudge signed-out users toward signing in — shown in `src/HomePage.tsx` once a user has SM-2 attempts/history to lose, and in `src/ProfilePage.tsx` in place of its old signed-out redirect. `src/quiz/SignInPromptModal.tsx` is the same idea as a dismissible modal (backdrop-click or "Not now" to close, same chrome as `src/quiz/ReportModal.tsx`) — `src/QuizPage.tsx` shows it once per results screen when a signed-out user finishes a test (tracked via a `promptedRef`, reset whenever `state.phase` leaves `"results"` so it can fire again on the next test).

### Stale-build detection (`src/UpdateModal.tsx`) + changelog (`/changelog`)

Next.js App Router client-side nav doesn't naturally refetch a newer deployment, so a backgrounded/bfcache'd tab can keep running an old JS bundle indefinitely (this was a real incident, not a hypothetical). `GET /api/version` (`app/api/version/route.ts`, `Cache-Control: no-store` + `export const dynamic = "force-dynamic"` — this endpoint must never be cached, or it can't detect a stale client) returns the live server's build SHA (`VERCEL_GIT_COMMIT_SHA` in `src/config.ts`, read fresh server-side, truncated to 7 chars like the existing client-side `GIT_COMMIT_SHA`) plus that SHA's release `message`/`releasedAt` looked up from the `releases` table (both `null` if no matching row — local dev, or a production build whose `postbuild` insert didn't run/failed). `UpdateModal` (mounted inside `QuizProvider` in `app/layout.tsx`, alongside `AuthSync` — it needs `useQuiz()`) compares the returned SHA against the client's bundled SHA on mount and on `focus`/`visibilitychange`, and shows a dismissible modal with the release's commit message (falling back to "The app has been updated." when `message` is `null`) on mismatch. Both SHAs are empty in local dev (`NEXT_PUBLIC_GIT_COMMIT_SHA`/`VERCEL_GIT_COMMIT_SHA` are only auto-set on Vercel), so the mismatch check requires both values non-empty — never a false positive locally (this also means `e2e/public/update-modal.spec.ts`'s SHA-mismatch tests can't actually trigger locally regardless of `/api/version` mocking — a known environment gap, not a regression). The modal never renders while `state.phase === "active"` (an in-progress quiz question) — gated at render time, not just at the check that sets it, since the async check can fire during `"loading"` before a question is on screen. Unlike the bottom-bar banner it replaced, the modal does **not** defer to `CookieBanner`'s consent gate — a centered overlay doesn't collide with `CookieBanner`'s fixed-bottom position the way two bottom bars would have. Dismissal is in-memory `useState` only, never persisted, and reload is always user-initiated (`window.location.reload()` on the Refresh button) — never automatic, since an in-progress quiz answer would be lost.

Release history is recorded automatically: `scripts/record-release.ts` runs as npm's `postbuild` step (wired in `package.json`, fires after every successful `next build`) and no-ops unless `process.env.VERCEL_ENV === "production"` — so it's a no-op for local builds and Vercel preview/branch deploys, only real production releases get recorded. It reads `VERCEL_GIT_COMMIT_SHA`/`VERCEL_GIT_COMMIT_MESSAGE` (both Vercel-provided build-time env vars) and upserts into the `releases` table (defined in `db/migrations/0000_baseline.sql` — see "Database migrations" above) with `ON CONFLICT (sha) DO NOTHING`, so a Vercel retry-build of the same commit is idempotent. No backfill of releases from before this feature shipped — the table starts empty and accumulates going forward. `GET /api/releases` (`app/api/releases/route.ts`) returns the full list ordered newest-first; `/changelog` → `src/ChangelogPage.tsx` (thin `app/changelog/page.tsx` wrapper, same route/component split as every other route) fetches it client-side and renders short SHA, formatted date, and commit message per release, with an explicit empty state ("No releases recorded yet.") until the first production deploy after this feature ships.

### Question feedback / reporting (`app/api/feedback/route.ts` + `src/quiz/ReportModal.tsx`)

`ReportModal` (opened from `FeedbackPanel`'s flag icon) offers 5 categories — 4 fixed (typo/wrong-info/confusing/duplicate) plus `"other"`, which reveals a free-text `<textarea maxLength={200}>` with a live counter; Submit stays disabled until non-empty (trimmed) text is entered for `"other"`. `POST /api/feedback` never trusts the client: `details` is only ever stored when `category === "other"` (forced `null` otherwise regardless of what the client sends), rejected with 400 (never silently truncated) if empty or over 200 raw characters, then control characters are stripped (`/[\x00-\x08\x0B\x0C\x0E-\x1F\x7F-\x9F]/g` — keeps real newlines/tabs and all printable Unicode) before storing in the `feedback.details` column. `feedback.ip` is captured on every row (not just anonymous ones) via `x-forwarded-for`.

Rate limiting is layered, backed by a dedicated `feedback_rate_limits` table (`key, window_start, count`, `PRIMARY KEY (key, window_start)`) via `getClientIp`/`incrementRateLimit` — shared helpers in `lib/rateLimit.ts` (extracted here so the general-feedback flow below can reuse them without duplication; this route imports them rather than defining its own). Each `incrementRateLimit` call is a single atomic `INSERT ... ON CONFLICT (key, window_start) DO UPDATE SET count = count + 1 RETURNING count` — Postgres row-locks the conflicting row, so concurrent requests for the same key genuinely serialize instead of racing a separate count-then-insert check (verified live against a real 20-concurrent-request burst: exactly 5 succeeded, 15 got 429). Windows are **fixed** (not sliding) as a deliberate atomicity tradeoff — a client could get up to ~2x a limit through across a window boundary, accepted as fine for a low-stakes public report form. Three independent limits are checked per request, any one triggering a 429: **per-identity** (`user_id` if signed in, IP if not — signed-in gets a higher ceiling since the identity is accountable/bannable, anonymous IPs are weaker/spoofable: 5 vs 2 per 10 minutes) and two **site-wide** caps across all identities combined (5/minute, 10/hour — keyed on fixed sentinel strings `__global_minute__`/`__global_hour__`, stops a distributed flood of many different identities each individually under their per-identity limit from still overwhelming the pipeline). All counters increment unconditionally, even on a request that ends up rejected by a *different* one of the three checks — a client can't probe a limit without the attempt counting. The `feedback.details`/`feedback.ip` columns and the `feedback_rate_limits` table are defined in `db/migrations/0000_baseline.sql` (see "Database migrations" above) — historically added via two now-deleted one-off scripts, folded into that baseline file.

`notifyTelegram` sends plain text with no `parse_mode`, so appended `details` text can't trigger markdown/HTML parsing — safe by construction, not by escaping.

### General app feedback (`app/api/app-feedback/route.ts` + `app/api/captcha/route.ts` + `src/AppFeedbackModal.tsx`)

A second, separate feedback surface — a "Send feedback" link on `HomePage.tsx` opens `AppFeedbackModal` for feedback about the app itself (not tied to a question), stored in its own `app_feedback` table (not the question-scoped `feedback` table — no `question_id`, no per-question dedup constraint). Same validation discipline as the question-report flow (reject-not-truncate at 200 raw chars, same control-char strip, `getClientIp`/`incrementRateLimit` from `lib/rateLimit.ts`), but with a **stricter, separately-namespaced** rate limit (`appfb:` key prefix — can't collide with the question-report flow's unprefixed keys, since they share the `feedback_rate_limits` table): 1/hour per identity, 5/hour site-wide, versus the question-report flow's 2-5/10min and 5/min+10/hr — general feedback has no question context to anchor abuse, so it's treated as more spam-attractive.

Also gated by a home-grown math CAPTCHA (no external service/account): `GET /api/captcha` picks two random 1-10 integers, stores `{token: randomUUID(), answer: a+b, expires_at}` in `captcha_challenges` (5-minute TTL), returns `{token, question}`. Verification (inside `POST /api/app-feedback`, not a separate endpoint) does `DELETE FROM captcha_challenges WHERE token = ... RETURNING answer, expires_at` **unconditionally** — right answer, wrong answer, expired, or nonexistent token all delete the row, making every token strictly single-use (no replay, no repeated guessing against one token). The CAPTCHA-issuing endpoint itself is deliberately ungated (no auth/rate-limit — cheap to issue), which would otherwise let `captcha_challenges` grow unboundedly; `GET /api/captcha` piggybacks an opportunistic `DELETE FROM captcha_challenges WHERE expires_at < now` sweep on every issue to keep it bounded.

`AppFeedbackModal` reloads a fresh CAPTCHA (`fetchCaptcha()` from `src/appFeedback.ts`) on mount and whenever a submission comes back `captcha_invalid` — `submitAppFeedback()`'s result type distinguishes `rate_limited`/`captcha_invalid`/`other` so the UI can show the right message (rate-limited and generic failures don't currently auto-reload the CAPTCHA, only `captcha_invalid` does — a retry after those two reuses the already-dead token and would need a manual close/reopen).

### Friends (`db/migrations/0001_friends.sql` + `app/api/friends/*` + `src/FriendsPage.tsx`/`src/FriendsAddPage.tsx`)

Users can invite friends and see a leaderboard ranked by overall accuracy. Two tables, both following `progress`'s bare-`TEXT`-`user_id`-no-FK convention (there's no app-owned `users` table to FK against — identity lives entirely in Neon Auth's `neon_auth."user"`, see "Neon migration" above): `friend_invite_tokens` (`user_id` PK — one persistent, reusable `randomUUID()` token per user, never rotated, `GET /api/friends/invite` is a get-or-create via `ON CONFLICT (user_id) DO UPDATE SET user_id = user_id` so `RETURNING` still fires on the existing row) and `friends` (accepted mutual friendships stored as **one row per direction**, composite `PRIMARY KEY (user_id, friend_id)` — chosen over a canonical-order single-row-per-pair scheme so every query is a trivial `WHERE user_id = $me`, matching how `progress`/`history` are already queried).

Visiting `/friends/add/[token]` (`src/FriendsAddPage.tsx`) and clicking "Add friend" is immediate, mutual, auto-accept — no pending/approval state. `POST /api/friends/add` inserts both `(me, inviter)` and `(inviter, me)` rows via two separate `ON CONFLICT DO NOTHING` statements (not a transaction — the Neon serverless driver's tagged-template calls are each their own round-trip); a partial failure between the two leaves an asymmetric one-directional row that self-heals the next time either side calls the endpoint again. Self-invites are rejected both client-side (`FriendsAddPage` hides the button when `inviterId === session.user.id`) and server-side (400, defense in depth). Re-adding an existing friend is a no-op success, not an error.

`GET /api/friends` (leaderboard) computes each entry's accuracy with the same `SUM(correct)::float / NULLIF(SUM(attempts), 0)` expression as `/api/stats/global` — left as independent inline SQL in both routes rather than extracted into a shared helper, matching the codebase's existing style of not abstracting one-off queries. Self is folded into the result set via a `UNION` in the CTE (no special-casing "add me to my own leaderboard"). Since there's no cascade on account deletion (`app/api/account/route.ts` only deletes the `neon_auth."user"` row — `progress`/`history`/`friends` rows are all left as accepted orphans), the leaderboard query `LEFT JOIN`s against `neon_auth."user"` and flags `accountDeleted` so the UI can render "Deleted user" instead of blank name/avatar while still ranking their (still-real) accuracy. `neon_auth."user".id` is `uuid`, not `text` (unlike every app-owned table's bare-`TEXT` `user_id`), so both this join and the one in `GET /api/friends/invite/[token]` must cast: `u.id::text = ids.user_id`.

`POST /api/friends/add` is rate-limited via the same `lib/rateLimit.ts` primitives as the feedback endpoints (`checkBanned`/`incrementRateLimit`/`recordViolationAndMaybeBan`), under a new `"friends-add"` endpoint namespace (20/hour per signed-in identity, configurable via `FRIENDS_ADD_RATE_LIMIT_MAX_PER_IDENTITY`/`FRIENDS_ADD_RATE_LIMIT_WINDOW_MINUTES` in `src/config.ts` — see "Repeat-offender ban" below) — it's the one write endpoint reachable by any signed-in user against any valid-looking token string, so it needs the same abuse guard as the feedback flows even though its ceiling is far more generous (legitimate use is "accept one invite").

The `/friends` nav link lives in `src/ProfilePage.tsx` (via `NavCard`) — not in `src/Header.tsx`, which has no precedent for a third nav destination (neither `/stats` nor `/friends` are linked from the header, only from `/profile`). `src/StatsPage.tsx` also renders a "You vs your friends" leaderboard (only when signed in — `authClient.useSession()`) reusing the same `GET /api/friends` response — this is deliberate, read-only duplication, not an oversight: `/stats` is the comprehensive, read-only "how am I doing" view (see "Stats vs Profile vs Friends" below), while `/friends` is the *management* surface — same leaderboard data, but each row also has a "Remove" action and the page owns the invite-link UI. `/stats`'s version has no remove action and links out to `/friends` at the bottom for management.

### Stats vs Profile vs Friends — page responsibilities

Three pages could plausibly show "your stats," so the split is deliberate, not incidental:
- **`/stats`** (`src/StatsPage.tsx`) is the single comprehensive analytics page, and works fully signed-out (reads `useProgress()`/`useHistoryState()`, both populated for anonymous users too — see "SM-2" above). It has *everything*: `Tests taken` + 4 `StatGauge`s (overall/recent/best/latest accuracy, `RECENT_WINDOW = 50` — kept in sync with `ProfilePage`'s old copy of the same constant, now only here), `ScoreChart`, `TopicAccuracyChart`, community comparison ("You vs average", twin gauges + delta), and the friends leaderboard. If a new personal stat is added anywhere, it belongs here — this is "all the stats," not "some of the stats." `ScoreChart.tsx` was rewritten 2026-08-02 (the old stacked-area/expanding-average-"Trend" design was removed the same day for the same reason, then rebuilt from scratch rather than patched): it's now a single-line `LineChart` plotting each test's score percentage on a fixed 0–100 axis, with an SVG gradient (`PassFailGradient`, using `useYScale`/`useDrawingArea`) filling the area green above and muted below `PASS_MARK = 75`, a labeled dashed reference line at the pass mark, and per-point marks colored `tokens.good`/`tokens.bad` via a custom `slots={{ mark: ScoreMark }}` MUI mark override (score ≥ 75 vs below).
- **`/profile`** (`src/ProfilePage.tsx`) is identity/account only: avatar, name, email, sign out, account deletion. It used to duplicate most of `/stats`'s charts — removed, since that duplication was the actual UX confusion (two pages both claiming to show "your progress," subtly out of sync). It's now a **navigation hub** via `src/NavCard.tsx` (a shared `{href, title, subtitle}` link-card, also used by `HomePage`) pointing to `/stats` ("Full statistics"), `/friends`, and `/propose-question` — no numbers duplicated here beyond a one-line live subtitle under "Full statistics" (`"{attempts} questions answered · {accuracy}% accuracy"`, sourced from the already-in-context `useProgress().aggregate`, not a new fetch).
- **`/friends`** (`src/FriendsPage.tsx`) is friend-list *management*: invite-link generation/copy, and a leaderboard whose rows have a "Remove" action. It's the only page that can mutate the friend list.

`src/NavCard.tsx`'s `subtitle` prop must be a block-level wrapper (`<div>`, not `<p>`) since callers pass arbitrary `ReactNode` — `HomePage`'s loading state passes a `<Skeleton>` (renders a `<div>`), and a `<div>` inside a `<p>` is invalid HTML (silently mis-parsed by the browser, breaks hydration matching). Don't change that wrapper back to `<p>`.

### Question proposals (`db/migrations/0002_question_proposals.sql` + `app/api/propose-question/route.ts` + `src/ProposeQuestionPage.tsx`)

Signed-in users can propose a brand-new question for the bank at the dedicated `/propose-question` page (not a modal, unlike `AppFeedbackModal`/`ReportModal` — this form has several optional fields — question text, up to 6 options, correct-answer checkbox(es), explanation, topic — that get cramped in a modal). Only `question` is required; `options`/`answer`/`explanation`/`topic` are all optional, but if any option is filled in the form (and server) requires **at least 2 non-empty options and at least one marked correct** before allowing submit — a partially-filled options list is rejected (400) rather than silently stored, both client-side (`canSubmit` in `ProposeQuestionPage.tsx`) and server-side (never trust the client). `topic` is a `<select>` sourced from `src/topics.ts`'s `TOPIC_ORDER` (closed enum, same taxonomy the `/questions` chip filter uses), not free text — keeps proposals aligned with the live topic set instead of producing values an admin has to manually remap.

Proposals land in `question_proposals` (`user_id, question, options JSONB, answer JSONB, explanation, topic, status, created_at` — same bare-TEXT `user_id`-no-FK convention as `progress`/`friends`) plus a best-effort Telegram notify (inline-duplicated `notifyTelegram`, same pattern as the two feedback routes — no shared helper exists in this codebase). **Review is entirely manual** — there's no in-app approve/reject UI; `status` (default `'pending'`) exists purely so a human reviewing the table via direct SQL can mark a row handled without deleting it, the same spirit as the `export:questions`/`sync:questions` manual review workflow (see "Question review/sync workflow" above). Rate-limited/banned the same way as `/api/friends/add` (single-tier, signed-in-only, no anonymous path): `proposeq:` key prefix on the shared `feedback_rate_limits` table, `"propose-question"` endpoint namespace for `identity_bans`/`rate_limit_violations`, defaults 5/hour per identity via `PROPOSE_QUESTION_RATE_LIMIT_MAX_PER_IDENTITY`/`PROPOSE_QUESTION_RATE_LIMIT_WINDOW_MINUTES` in `src/config.ts`.

### Repeat-offender ban + configurable rate limits

Both feedback endpoints (plus `/api/friends/add` and `/api/propose-question`, see "Friends"/"Question proposals" above) escalate: if the same identity (`user_id` if signed in, else IP) gets rejected by its **per-identity** rate limit 3 times within a rolling hour, that identity is banned from that specific endpoint for 24h — each route tracks violations/bans **independently** via an `endpoint` column (`"feedback"`/`"app-feedback"`/`"friends-add"`/`"propose-question"`), backed by `rate_limit_violations` (append-only log) and `identity_bans` (`key, endpoint, banned_until`, composite PK, upserted). `checkBanned`/`recordViolationAndMaybeBan` (`lib/rateLimit.ts`) are called first thing in each route — before any validation/CAPTCHA/DB write — and a violation is logged only on a per-identity rejection, never a global-limit-only one. `/api/app-feedback` requires care here: its `feedback_rate_limits` keys are `appfb:`-prefixed to avoid colliding with `/api/feedback`'s own, but the ban tables must use the **raw, unprefixed** identity (the `endpoint` column does that namespacing instead) — a separate `rawIdentity` variable is kept distinct from the prefixed `identityKey` used only for `incrementRateLimit`. A `403 { error: "banned" }` response is mapped client-side to the same `rateLimited`/`rate_limited` reason as a `429`, in both `src/feedback.ts` and `src/appFeedback.ts` — no separate ban-specific UI copy.

`lib/rateLimit.ts`'s three functions each piggyback an opportunistic sweep of their own table on every call — same pattern as `captcha_challenges`' sweep in `GET /api/captcha` (see "General app feedback" above): `incrementRateLimit` sweeps `feedback_rate_limits` rows with `window_start` older than 24h, `checkBanned` sweeps `identity_bans` rows with `banned_until` in the past, `recordViolationAndMaybeBan` sweeps `rate_limit_violations` rows with `occurred_at` older than 24h. The 24h cutoffs are a safe buffer, not tightly coupled to the 1h `BAN_VIOLATION_WINDOW_MS` lookback or the longest 1h rate-limit window — no cron job, all three tables stay bounded purely from being hit by normal traffic on the rate-limited endpoints.

All rate-limit/ban numeric thresholds (15 total — `/api/feedback`/`/api/app-feedback`'s per-identity/global limits, `/api/friends/add`'s and `/api/propose-question`'s per-identity limit/window, plus the ban's violation threshold/window/duration) are environment-configurable via `src/config.ts`, following the same `Number(process.env.X) || default` pattern as `SESSION_SIZE` — unset or invalid falls back silently to the value that was previously hardcoded, no startup validation. Window durations are expressed as `_MINUTES`/`_HOURS` env vars (e.g. `FEEDBACK_RATE_LIMIT_WINDOW_MINUTES`) for operator readability, converted to ms once in `src/config.ts`. Deliberately **not** configurable: `/api/feedback`'s two global window *durations* (fixed 1min/1hr — their key literals `__global_minute__`/`__global_hour__` embed that duration, so decoupling the duration from the name risks a misleading mismatch) and `MAX_DETAILS_LENGTH` in both feedback routes (unrelated to rate-limiting). All vars are documented (commented-out, with defaults) in `.env.example`.
